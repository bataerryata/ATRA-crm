# طراحی فنی دیتابیس ATRA

- وضعیت سند: پیش‌نویس فنی برای بازبینی مالک
- تاریخ: 2026-11-10
- مخزن: `bataerryata/ATRA-crm`
- شاخه: `docs/atra-requirements-and-design-roadmap`
- وضعیت اجرا: **صرفاً مستندات؛ هیچ SQL یا Migration اجرا نشده است.**
- مبنای تصمیم: پشتیبانی از اشخاص حقیقی و کسب‌وکارها؛ دسترسی به اطلاعات حساس برای همه کاربران مجاز پرونده؛ تعداد نامحدود اشخاص مرتبط.

## 1. هدف و محدوده

این سند مدل داده پیشنهادی CRM را به سطح فنی قابل تبدیل به PostgreSQL/Supabase می‌رساند. این سند مجوز اجرای SQL، ایجاد جدول، انتقال اطلاعات، تغییر تنظیمات Supabase یا انتشار برنامه نیست.

سه مفهوم باید از هم جدا بمانند:

1. **Party / هویت:** شخص حقیقی یا کسب‌وکار.
2. **Market Lead / سرنخ بازار:** یک فرصت بالقوه یا رکوردی از بانک اطلاعات بازار؛ هنوز لزوماً مشتری شرکت نیست.
3. **Customer / مشتری احرازشده:** پرونده تجاری فعال یا غیرفعال یک هویت که پس از بررسی به‌عنوان مشتری ثبت شده است.

اطلاعات فایل بانک بازار ابتدا در ناحیه واردسازی نگهداری می‌شود. رکوردها بدون بررسی و تأیید به مشتری تبدیل نمی‌شوند.

## 2. تصمیم‌های قطعی مالک

| موضوع | تصمیم |
|---|---|
| دامنه هویت | شخص حقیقی و کسب‌وکار |
| دسترسی خواندن اطلاعات حساس | همان کاربران مجاز به مشاهده پرونده مربوط |
| تعداد اشخاص مرتبط | نامحدود |
| تخصیص مشتری | فقط مدیر فروش؛ تخصیص خودکار ممنوع |
| کارشناسان هر مشتری | امکان تخصیص هم‌زمان چند کارشناس |
| اولویت مشتری | تعیین توسط مدیر فروش؛ تغییر خودکار ممنوع |
| غیرفعال‌سازی مشتری | مدیر فروش و مدیرعامل؛ بدون حذف سوابق |
| سقف اعتبار گروه | مقدار پیشنهادی اولیه؛ تغییر گروه یا گروه نباید اعتبار موجود را خودکار تغییر دهد |
| فایل بانک بازار | سرنخ بازار، نه مشتری قطعی |
| حسابداری | محک مرجع اصلی؛ اتصال احتمالی در ابتدا فقط خواندنی |

## 3. قواعد عمومی مدل داده

- کلید اصلی جداول عملیاتی: `UUID` با تولید در PostgreSQL.
- کلیدهای خارجی: همان نوع UUID و با قیدهای صریح.
- زمان‌های رخداد: `TIMESTAMPTZ` با ذخیره‌سازی UTC؛ نمایش محلی در برنامه.
- تاریخ‌های تقویمی بدون ساعت: `DATE`.
- تلفن، کد ملی، شناسه ملی، شماره ثبت، کد اقتصادی، کدپستی و کدهای مرجع: `TEXT`؛ نه عدد.
- مبلغ‌ها: `NUMERIC(18,2)`؛ قرارداد ذخیره‌سازی مبلغ در ATRA تومان است و تبدیل ریال/تومان در مرز اتصال به سامانه‌های دیگر باید صریح باشد.
- داده‌های ساختاریافته تکمیلی و snapshotهای واردسازی: در صورت نیاز `JSONB`؛ نه به‌عنوان جایگزین ستون‌های اصلی و قابل جست‌وجو.
- تمام جداول عملیاتی دارای `created_at` و در صورت نیاز `updated_at` باشند. زمان ایجاد/ویرایش و شناسه کاربر از سمت سرور ثبت شوند.
- حذف فیزیکی مشتری، اسناد صادرشده، فعالیت‌ها و سوابق مالی در عملیات عادی مجاز نیست؛ از وضعیت، لغو یا بایگانی استفاده شود.
- تاریخ میلادی/استاندارد در دیتابیس ذخیره می‌شود؛ تبدیل و نمایش شمسی در لایه رابط کاربری انجام می‌شود.
- نام جدول‌ها و ستون‌ها انگلیسی و snake_case؛ برچسب‌های رابط کاربری فارسی.

## 4. مدل هویت مرکزی

### 4.1 `parties`

هر رکورد نماینده یک هویت مستقل است.

| ستون | نوع | الزام | توضیح |
|---|---|---|---|
| `id` | UUID | PK | شناسه هویت |
| `party_type` | TEXT | NOT NULL | فقط `individual` یا `business` |
| `display_name` | TEXT | NOT NULL | نام نمایشی برای فهرست‌ها |
| `created_at` | TIMESTAMPTZ | NOT NULL | زمان ایجاد |
| `updated_at` | TIMESTAMPTZ | NOT NULL | زمان آخرین تغییر |
| `created_by` | UUID | FK به profiles.id، nullable برای سرویس سیستمی | ایجادکننده |

قید: `party_type` با CHECK محدود شود. هر party دقیقاً یک پروفایل متناظر داشته باشد؛ کنترل این قاعده با trigger یا تابع تراکنشی انجام شود، زیرا CHECK معمولی نمی‌تواند سازگاری بین دو جدول را تضمین کند.

## 5. سرنخ بازار و مشتری

### 5.1 `market_leads`

یک party می‌تواند در طول زمان چند سرنخ یا سابقه منبع جذب داشته باشد؛ بنابراین `party_id` در این جدول unique نیست.

| ستون | نوع | توضیح |
|---|---|---|
| `id` | UUID PK | شناسه سرنخ |
| `party_id` | UUID FK → parties.id، nullable | هویت تطبیق‌داده‌شده؛ در زمان واردسازی ممکن است خالی باشد |
| `lead_status` | TEXT | وضعیت پیگیری سرنخ |
| `source_type` | TEXT | منبع جذب |
| `source_reference` | TEXT | شناسه/مرجع بیرونی |
| `priority` | TEXT | اولویت، در صورت تعریف سیاست |
| `qualification_status` | TEXT | نتیجه ارزیابی |
| `created_at` | TIMESTAMPTZ | زمان ایجاد |
| `created_by` | UUID FK → profiles.id | ایجادکننده |
| `notes` | TEXT | توضیحات |

مقادیر وضعیت سرنخ فعلاً پیشنهادی‌اند و باید پیش از Migration به‌عنوان فهرست نهایی تأیید شوند.

### 5.2 `customers`

| ستون | نوع | توضیح |
|---|---|---|
| `id` | UUID PK | شناسه پرونده مشتری |
| `party_id` | UUID UNIQUE/FK → parties.id | هر هویت حداکثر یک پرونده مشتری |
| `customer_code` | TEXT UNIQUE | کد داخلی مشتری |
| `customer_group_id` | UUID FK → customer_groups.id، nullable | گروه مشتری |
| `customer_status` | TEXT | وضعیت مشتری |
| `priority` | TEXT | اولویت تعیین‌شده توسط مدیر فروش |
| `credit_limit` | NUMERIC(18,2) | سقف اعتبار فعلی، به تومان |
| `payment_terms` | TEXT | شرایط پرداخت فعلی؛ جزئیات می‌تواند در جدول تاریخچه باشد |
| `activated_at` | TIMESTAMPTZ | زمان فعال‌سازی |
| `deactivated_at` | TIMESTAMPTZ | زمان غیرفعال‌سازی |
| `deactivation_reason` | TEXT | دلیل غیرفعال‌سازی |
| `created_at` | TIMESTAMPTZ | زمان ایجاد |
| `created_by` | UUID FK → profiles.id | ایجادکننده |

قواعد:
- `party_id` یکتا است؛ هر هویت فقط یک پرونده مشتری دارد.
- غیرفعال‌سازی به‌جای حذف انجام می‌شود.
- فقط مدیر فروش و مدیرعامل مجاز به فعال/غیرفعال‌سازی هستند.
- تغییر گروه، مقدار اعتبار مشتری را خودکار بازنویسی نمی‌کند.
- اعتبار پیشنهادی گروه هنگام ایجاد مشتری فقط مقدار اولیه پیشنهادی است؛ پس از ثبت، مستقل می‌شود.

### 5.3 `lead_conversions`

| ستون | نوع | توضیح |
|---|---|---|
| `id` | UUID PK | شناسه تبدیل |
| `lead_id` | UUID UNIQUE/FK → market_leads.id | هر سرنخ حداکثر یک‌بار تبدیل شود |
| `customer_id` | UUID FK → customers.id | پرونده مقصد |
| `converted_at` | TIMESTAMPTZ | زمان تبدیل |
| `converted_by` | UUID FK → profiles.id | کاربر انجام‌دهنده |
| `conversion_notes` | TEXT | توضیح/مبنای تبدیل |

چند سرنخ می‌توانند به یک مشتری موجود مرتبط شوند، اما هر سرنخ فقط یک بار تبدیل می‌شود. تبدیل باید در یک تراکنش انجام شود تا ایجاد مشتری و ثبت سابقه تبدیل نیمه‌کاره نماند.

- یکتایی شخص اصلی در هر کسب‌وکار یا در هر نقش، تا تعیین قانون دقیق کسب‌وکار به‌صورت قید سخت اعمال نمی‌شود.

## 7. فعالیت‌ها، تخصیص و وظایف

### 7.1 `customer_assignments`

| ستون | نوع | توضیح |
|---|---|---|
| `id` | UUID PK | شناسه تخصیص |
| `customer_id` | UUID FK → customers.id | مشتری |
| `user_id` | UUID FK → profiles.id | کارشناس |
| `assignment_role` | TEXT | نوع مسئولیت |
| `is_primary` | BOOLEAN | مسئول اصلی |
| `assigned_at` | TIMESTAMPTZ | زمان تخصیص |
| `assigned_by` | UUID FK → profiles.id | تخصیص‌دهنده |
| `ended_at` | TIMESTAMPTZ | پایان تخصیص؛ nullable |
| `notes` | TEXT | توضیح |

تخصیص جدید فقط با مجوز مدیر فروش. تخصیص‌های قبلی حذف نمی‌شوند و با `ended_at` بسته می‌شوند. مسئول فرصت فروش و اسناد فروش در جداول همان ماژول‌ها به‌طور مستقل ثبت می‌شود.

### 7.2 `lead_activities` و `customer_activities`

هر دو جدول باید ساختار مشابه داشته باشند: شناسه، شناسه سرنخ/مشتری، نوع فعالیت، عنوان، شرح، زمان رخداد، کاربر ثبت‌کننده، نتیجه و زمان ایجاد. از یک جدول polymorphic با `entity_type/entity_id` بدون FK واقعی استفاده نشود.

### 7.3 `customer_notes`

شناسه، customer_id، عنوان، متن، سطح محرمانگی در صورت نیاز، ایجادکننده، زمان ایجاد و زمان ویرایش. اگر یادداشت‌ها می‌توانند فقط برای نویسنده یا گروه خاص باشند، قانون آن باید در ماتریس مجوزها تعریف شود.

### 7.4 `tasks`

شناسه، عنوان، شرح، وضعیت، اولویت، موعد، مسئول، ایجادکننده، زمان تکمیل و ارتباط اختیاری با مشتری یا سرنخ. در نسخه SQL باید قید شود که وظیفه حداقل یک زمینه معتبر دارد و ارجاع آن به مشتری و سرنخ با FKهای واقعی انجام شود؛ طراحی polymorphic آزاد بدون کنترل پیشنهاد نمی‌شود.

## 8. قیمت‌گذاری و اعتبار

### 8.1 `customer_pricing_rules`

فیلدهای پایه: شناسه، customer_id، product_id، price_amount، currency_code، valid_from، valid_until، status، created_by، approved_by، approved_at، notes، created_at.

- قیمت به‌صورت NUMERIC ذخیره شود.
- اعتبار زمانی می‌تواند بدون تاریخ پایان باشد.
- قیمت‌های متداخل برای یک مشتری و یک محصول باید هنگام انتخاب قیمت مدیریت شوند؛ جلوگیری از تداخل با exclusion constraint فقط پس از قطعی‌شدن منطق انتخاب و پایگاه داده قابل اجراست.
- تغییر قیمت نباید اسناد صادرشده قبلی را تغییر دهد.
- قیمت و شرایط نهایی هر پیش‌فاکتور/سفارش باید در همان سند snapshot شوند.
- تأیید موردی قیمت اختصاصی و حدود اختیار مدیر فروش هنوز نیازمند تعیین تکلیف است.

### 8.2 `customer_credit_history`

شناسه، customer_id، previous_limit، new_limit، changed_at، changed_by، reason، source_type، source_id. هر تغییر اعتبار باید هم مقدار جدید در customers و هم رویداد تاریخچه را در یک تراکنش ثبت کند.

### 8.3 `customer_payment_terms_history`

شناسه، customer_id، previous_terms، new_terms، changed_at، changed_by، reason. شرایط پرداخت فعلی در customers یا یک رکورد فعال از تاریخچه قابل دسترسی است؛ منبع حقیقت باید هنگام SQL فقط یک‌بار انتخاب شود.

## 9. واردسازی بانک اطلاعات بازار

### 9.1 `lead_import_batches`

شناسه، نام فایل منبع، checksum فایل، زمان شروع، شروع‌کننده، وضعیت پردازش، تعداد رکوردها، تعداد موفق، تعداد خطا و گزارش خلاصه.

### 9.2 `lead_import_records`

شناسه، batch_id، شماره ردیف منبع، شماره صفحه PDF، raw_data JSONB، وضعیت بررسی، فیلدهای نیازمند بررسی، دلیل ابهام، شناسه رکورد مشابه پیشنهادی، market_lead_id nullable، خطای پردازش و زمان بررسی.

قواعد:
- فایل اصلی دست‌نخورده باقی بماند.
- رکورد خام و مقادیر منبع حفظ شوند.
- تشخیص تکرار فقط پیشنهاد است؛ ادغام/حذف خودکار ممنوع.
- رکورد فاقد نام یا شناسه معتبر می‌تواند در staging باقی بماند.
- تبدیل به party/lead/customer مرحله‌ای و قابل ممیزی باشد.
- اختلاف تعداد ردیف‌های فایل و تعداد رکوردهای پردازش‌شده باید گزارش شود.

## 10. مدارک و ذخیره‌سازی فایل

### `customer_documents`

شناسه، customer_id، document_type، file_name، storage_bucket، storage_path، mime_type، file_size، uploaded_by، uploaded_at، document_date، notes.

- Bucket خصوصی باشد.
- دانلود فقط از مسیر احراز هویت‌شده و پس از بررسی مجوز پرونده انجام شود.
- مسیر فایل و نام آن به‌تنهایی مجوز دسترسی نیست.
- حذف فایل/مدرک نیازمند سیاست نگهداری و مجوز مشخص است؛ تا آن زمان حذف فیزیکی در گردش عادی فعال نشود.

## 11. تاریخچه ممیزی

### `audit_logs`

شناسه، actor_user_id، action, entity_type، entity_id، occurred_at، request_id، before_data JSONB، after_data JSONB، reason.

- درج از سمت سرور/trigger یا مسیر قابل اعتماد انجام شود.
- کاربر عادی اجازه UPDATE/DELETE لاگ را نداشته باشد.
- کد ملی، شماره شناسنامه، توکن‌ها، رمزها و داده‌های حساس غیرضروری در before/after ذخیره نشوند؛ برای این فیلدها فقط رخداد تغییر و شناسه رکورد ثبت شود.
- زمان و کاربر از ورودی قابل دستکاری مرورگر به‌تنهایی پذیرفته نشود.

## 12. کاربران، نقش‌ها و مجوزها

### جداول

- `profiles`: شناسه برابر `auth.users.id`، نام نمایشی، وضعیت حساب و زمان‌ها.
- `roles`: شناسه، کد یکتا، نام فارسی، توضیح.
- `permissions`: شناسه، کد یکتا مانند `customer.read`، توضیح.
- `role_permissions`: role_id و permission_id با قید unique ترکیبی.
- `user_roles`: user_id و role_id با قید unique ترکیبی.

نقش‌های اولیه شامل مدیرعامل، مدیر فروش، کارشناس فروش، مدیر تولید، مسئول مونتاژ، مسئول کنترل کیفیت، مسئول تحویل، مسئول مالی و مدیر سیستم هستند. ماتریس نهایی مجوزهای هر نقش هنوز تأیید نشده است.

## 13. سیاست دسترسی و RLS

RLS برای تمام جداولی که از کلاینت قابل دسترسی‌اند فعال و با سیاست‌های صریح اعمال شود. مخفی‌کردن دکمه در UI کنترل امنیتی محسوب نمی‌شود.

مجوزهای پیشنهادی در سطح قابلیت:
- `customer.read`
- `customer.create`
- `customer.update`
- `customer.deactivate`
- `customer.assign`
- `customer.sensitive.update`
- `lead.read`
- `lead.create`
- `lead.update`
- `lead.convert`
- `customer.pricing.read`
- `customer.pricing.manage`
- `customer.credit.read`
- `customer.credit.manage`
- `audit.read`

قاعده مورد تأیید مالک برای اطلاعات حساس:
- اگر کاربر مجاز به مشاهده پرونده مربوط باشد، مجاز به مشاهده اطلاعات حساس همان پرونده نیز هست.
- ویرایش اطلاعات حساس مجوز جداگانه و محدودتر می‌خواهد.
- جداول حساس نباید از طریق view یا API بدون RLS در دسترس قرار گیرند.
- برای بررسی مجوزهای پیچیده از توابع کمکی امن با `SECURITY DEFINER` فقط در صورت نیاز، با `search_path` ثابت، حداقل دسترسی و تست دقیق استفاده شود.
- هیچ‌گاه service_role key در مرورگر قرار نگیرد.
- نقش مدیر سیستم به‌صورت خودکار مجوز مشاهده تمام اطلاعات مالی یا حساس نمی‌گیرد؛ این موضوع باید صریحاً در ماتریس نقش‌ها تعیین شود.

RLS نهایی تا زمان تأیید ماتریس نقش‌ها و دامنه مشاهده مشتریان توسط کاربران غیرمسئول، قابل نهایی‌سازی نیست.

## 14. قیود و شاخص‌های پیشنهادی

قیود پایه:
- FKها با رفتار حذف محافظه‌کارانه؛ برای سوابق تجاری `ON DELETE CASCADE` استفاده نشود.
- unique روی `customers.party_id` و `customers.customer_code`.
- unique روی `person_profiles.party_id` و `business_profiles.party_id`.
- CHECK روی party_type، مقادیر عددی غیرمنفی و بازه تاریخ‌ها.
- index روی FKها و فیلدهای پرتکرار جست‌وجو: نام نمایشی، نام کسب‌وکار، نام خانوادگی، شماره تماس نرمال‌شده، کد مشتری، وضعیت، گروه و زمان ایجاد.
- جست‌وجوی فارسی باید با نرمال‌سازی ی/ي و ک/ك، فاصله و نیم‌فاصله بررسی شود؛ نسخه اصلی متن حفظ شود.
- برای تلفن/کد ملی unique سراسری اعمال نشود، مگر پس از تأیید قواعد یکتایی؛ شماره مشترک و داده تکراری بازار ممکن است وجود داشته باشد.
- برای مقادیر enum، در فاز اول CHECK یا lookup table انتخاب شود؛ وضعیت‌هایی که احتمال تغییر مدیریتی دارند بهتر است lookup table داشته باشند.

## 15. تصمیم‌های باز پیش از Migration

این موارد مانع طراحی مفهومی نیستند، اما قبل از تولید SQL اجرایی باید تعیین تکلیف شوند:

1. ماتریس کامل نقش‌ها و مجوزها، به‌ویژه مشاهده مشتریان تخصیص‌نیافته و اطلاعات مالی.
2. فهرست نهایی وضعیت‌های سرنخ، مشتری، فعالیت و وظیفه.
3. تعریف دقیق گروه‌های مشتری و نام/معیار آنها.
4. حدود عددی اختیار مدیر فروش در قیمت و تخفیف و موارد ارجاع به مدیرعامل.
5. آیا قیمت اختصاصی مشتری نیازمند تأیید موردی مدیرعامل است یا در محدوده اختیار تفویض‌شده قرار می‌گیرد؟
6. تعریف واحد و بازه `estimated_purchase_volume`.
7. سیاست نگهداری، دانلود و حذف مدارک.
8. تعریف یکتایی شخص اصلی و راه تماس اصلی.
9. مدل اتصال آدرس و تماس به شعبه در کنار party.
10. نحوه ثبت و نگهداری داده‌های حساس (رمزنگاری سطح ستون و مدیریت کلید) با توجه به نیاز واقعی و هزینه عملیاتی.

## 16. ترتیب پیشنهادی Migration

پس از تأیید سند و تصمیم‌های مسدودکننده:

1. جداول پایه کاربران/نقش‌ها و هویت مرکزی.
2. پروفایل اشخاص و کسب‌وکارها و اطلاعات حساس.
3. گروه‌ها، مشتریان، سرنخ‌ها و تبدیل.
4. تماس‌ها، آدرس‌ها، روابط اشخاص و شعب.
5. تخصیص‌ها، فعالیت‌ها، وظایف و ترجیحات.
6. قیمت‌گذاری و تاریخچه اعتبار/شرایط پرداخت.
7. واردسازی، مدارک و audit log.
8. RLS، توابع کمکی و تست سیاست‌ها.
9. تست constraintها، سناریوهای تبدیل، دسترسی‌ها و rollback.

هر مرحله باید migration مستقل، قابل بازبینی و تا حد امکان برگشت‌پذیر داشته باشد. قبل از اجرا روی `atra-dev`، SQL هر مرحله، اثر آن و روش بازگشت جداگانه به مالک ارائه و تأیید گرفته شود.

## 17. معیار پذیرش طراحی

- شخص حقیقی و کسب‌وکار بدون اختلاط اطلاعات قابل ثبت باشند.
- یک کسب‌وکار بتواند تعداد نامحدودی شخص مرتبط داشته باشد.
- یک شخص بتواند به چند کسب‌وکار مرتبط باشد.
- سرنخ بازار بدون تبدیل، مشتری محسوب نشود.
- تبدیل سرنخ، تاریخچه و منبع را حفظ کند.
- یک مشتری چند کارشناس داشته باشد و تاریخچه تخصیص حفظ شود.
- غیرفعال‌سازی مشتری هیچ سابقه تجاری را حذف نکند.
- اطلاعات حساس فقط برای کاربران مجاز پرونده قابل خواندن باشد.
- کاربر غیرمجاز نتواند با REST API یا Storage مسیر مستقیم، محدودیت UI را دور بزند.
- تغییر قیمت و اعتبار با کاربر، زمان و مقدار قبل/بعد قابل ممیزی باشد.
- تغییر قیمت جاری اسناد قبلی را تغییر ندهد.
- فایل واردسازی خام حفظ شود و ادغام تکراری‌ها بدون تأیید انجام نشود.

## 18. مرز این سند

این سند طراحی پیشنهادی دیتابیس است؛ اثبات‌کننده وجود جدول‌ها یا قابلیت‌ها در Supabase نیست. در زمان تهیه سند، طبق ممیزی خواندنی ثبت‌شده، در schema عملیاتی public جدول CRM و migration اختصاصی ATRA مشاهده نشده بود. وضعیت باید پیش از هر اجرای واقعی دوباره بررسی شود.

**هیچ SQL، Migration، جدول، policy، storage bucket یا داده‌ای در نتیجه تهیه این سند ایجاد یا تغییر داده نشده است.**
